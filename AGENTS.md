# Repository Guidelines

## Scope & Design Boundaries

MWU is a generic UI for [MaaFramework](https://github.com/MaaXYZ/MaaFramework), used by one person locally or on a trusted LAN. It is not a public, multi-user, or multi-tenant service; LAN access from another device does not change that. Users bring their own `resource/`, `interface.json`, and `agent/` as integration inputs: improve the generic loader/runtime, never bake in project-specific resources, tasks, or agent behavior.

Write the simplest correct implementation and preserve the backend/frontend API contract. No accounts, permission hierarchies, tenant isolation, distributed coordination, generic frameworks, compatibility layers, or abstractions without a current concrete need. Keep safeguards for real failure modes: malformed config, unsafe paths, interrupted writes, cancellation, subprocess cleanup, overlapping manual/scheduled runs, and background threads. Validate at the boundary and surface failures; avoid re-validating normalized internal data, blanket exception suppression, silent fallbacks, and retries without demonstrated need.

## Layout

- Backend: `main.py` (CLI entry: args, single-instance check, native-dispatch delegation, `uvicorn.run`), `backend/runtime.py` (process-level singletons: app root, interface/language loading, `AppState`), `backend/app.py` (FastAPI assembly, lifespan, static/SPA hosting, router registration), `backend/api/` (domain APIRouters: interface/scan-select, device/stream, settings/task-config, update/shutdown, run/log SSE, scheduler), `backend/core/` (`paths.py`, `state.py`, `settings_io.py`, `secret_store.py`, `json_utils.py`), `backend/maa_worker/` (`execution.py` admission/preparation/cancellation/history, `worker.py` MAA runtime composition, `pretask_service.py`, other MAA services, sink/focus), `backend/scheduler/` (APScheduler CRUD + native wakeup coordination), `backend/services/` (update, telemetry), `backend/models/` (Pydantic, interface/task-config normalization).
- Frontend `front/src/`: `app/` (bootstrap, router, i18n, theme), thin route `views/`, domain-grouped `components/` (shared controls in `common/`), domain Pinia `stores/`, `services/` (api/feedback/realtime), `validation/`, `types/`, `utils/`. Vite builds to `page/`.
- `.github/workflows/`: MWU's own test/release packaging. `updater/`: Go updater. `deploy/`: packaging template and scripts for downstream projects that consume an MWU release, not MWU's own pipeline; `deploy/install.yml` is a drop-in replacement for MaaPracticeBoilerplate's `.github/workflows/install.yml` (flattens `assets/` plus `agent/`, `README.md`, `LICENSE` onto an extracted MWU release; assets named `<repo>-<os>-<arch>-<tag>.7z`).

## Architecture

- **Hosting**: `backend/runtime.py` resolves the app root (`APP_ROOT_DIR`: `page/`, `config/`, `agent/`, `deps/`, MAA toolkit and agent-subprocess cwd) and the project dir (`PROJECT_DIR`: `interface.json` and every PI-relative path); packaged both are the executable's directory, from source the project dir is `assets/` (MaaPracticeBoilerplate source layout; local test data is gitignored). It loads/validates `interface.json` and language files; `backend/app.py` builds the singleton runtime in lifespan (`MaaWorker`, realtime broadcaster, history store, `SystemScheduler`, `SchedulerManager`); native registrations converge while APScheduler is paused, then it resumes. Routes live in `backend/api/`. `main.py` is the CLI entry (argument parsing, single-instance port check, native-dispatch delegation, `uvicorn.run`); Uvicorn binds `0.0.0.0:5566`, while browser launch and native-dispatch delegation use loopback. `/assets` serves `page/assets`, `/resource` the project's `resource/` tree, the SPA fallback `page/index.html`; `/api/file` serves and `/api/file/list` lists one level of only project-dir-contained paths (a leading `./` is dropped; `..`, empty segments, absolute/drive paths are rejected; listed entries whose symlink target escapes the project dir are omitted).
- **State and DI**: `AppState` owns the broadcaster/history, settings, device/task/agent/focus state, the `active_run` slot and coroutine, update gate/status, scheduler refs, and shutdown state; `WorkerContext`, pending modals, and `ActiveRun` also live in `backend/core/state.py`. `MaaWorker` is a DI container, not a service: module-level CPU `Resource` singleton, per-runtime `Tasker` and HTTP client, state aliases, and services `events`/`focus`/`device`/`pipeline`/`agents`/`pretasks`/`tasks`/`sinks`/`text`, which collaborate through the worker back-reference.
- **Persistence**: settings and task-config writes encrypt first, then go through `backend/core/settings_io.atomic_write_json` (tmp+fsync+replace under `SETTINGS_LOCK`), so a failed save keeps the old file. `/api/settings` POST force-preserves `panel.customDevices`. Option `input` fields marked `password` are Fernet-encrypted at rest by `backend/core/secret_store.py` (key in the per-user data dir) in `settings.json`, `task_config.json`, and APS job kwargs; they stay plaintext in memory and API responses. APS jobs and execution history share `config/scheduler.sqlite`.
- **Build/package**: packaged apps combine `page/`, a Nuitka standalone backend, MaaAgentBinary, and the platform Go updater.

### Execution

- **Pipeline**: manual, in-app scheduled, and native scheduled starts all enter `backend/maa_worker/execution.py`. `_complete_run` admits into the single slot, normalizes the payload (at least one valid task required before any command runs), runs interface `pretask` executables (args/option payloads, no timeout; only stop ends them) and then user `PreTaskCommand` shell commands (configured timeout), prepares device/resource (skipped when reusing a locked connection), runs `TaskService`, writes history, and clears the slot. Pre-task failure aborts before MAA tasks. `PretaskService` owns output capture, timeout, stop polling, and process termination.
- **Keep awake**: every admitted run executes inside wakepy `keep.running` (`_run_keep_awake` wraps `_complete_run`), which blocks system sleep but not screen-off; activation failure is logged and the run continues. wakepy modes are not thread-safe, so enter and exit stay in the event-loop coroutine. `backend/maa_worker/keep_awake.py` swaps wakepy's Windows method for a subclass that releases its inhibitor thread when activation fails (wakepy 1.0.0 leaves that non-daemon thread waiting forever, blocking process exit).
- **Stop lifecycle**: `_claim_slot` resets `stop_flag` on admission; never reset it later during preparation or startup, or a stop request is lost. `TaskService.run_process()` polls stop before, during, and after MAA tasks; `PretaskService` polls while subprocesses run. Cancelling during pre-tasks must drain the shielded pre-task future before clearing `active_run`, or a new run could reset the shared flag while old commands still run.
- **Terminal-event ordering**: `run_process()` records status but emits no terminal events. `_complete_run` emits `task.completed`/`task.failed` after history, with slot clearing and `EventService.publish_task_terminal` in one synchronous segment (no `await` between), so a new run's `task.started` cannot precede the old terminal event; notifications follow in a worker thread. The subject uses the label captured at start. A start issued after the frontend sees a terminal event is admitted.
- **`configuration_locked`**: set when `set_resource()` succeeds after connect; while the connection stays live, locked `connect()`/`set_resource()` refuse. `reset_connection_state()` releases it on connection/liveness/screencap failure and when execution must replace an incompatible connection.
- **Agents**: startup is lazy and one-shot via `AgentService.ensure_started_once()` in `TaskService.start()`; `started_once` ratchets even after failure, and external processes connected earlier in the batch are cleaned up before the aggregate error is retained. Embedded Python agents (`backend/maa_worker/agent_loader.py`) use a custom module finder, `deps/` precedence, the `_BlackMagicAgentServer` stub (keeps the library in client mode during in-process import), regex/AST registration, and in-process instances; external agents use `AgentClient` + subprocesses.
- **Decorator regex is fragile**: only `@AgentServer.custom_action("...")` / `@AgentServer.custom_recognition("...")` with double quotes match, and the `class` line must immediately follow the decorator. Anything else fails silently.
- **Task identity**: execution lists and option-map keys use unique `task.name`, not `task.entry`. A queue may repeat a name; repeats share one option map and run in order, while UI selection/removal uses per-entry `uid` (regenerated on hydration, not persisted). `task.entry` may repeat across definitions and is resolved only at `tasker.post_task`. `active_run.task_name` is a display label (first task, or schedule name), not a lookup key.

### Interface and options

- **Loader** (`backend/models/interface_loader.py`): root uses the full schema; imported fragments may contain only `task`/`option`/`preset`/`pretask`/`import`/`global_option`/`setting`. Imports resolve from the app root; duplicate task names/presets and absolute/parent/drive/UNC escapes fail loudly; a later option key overrides an earlier one; groups dedupe by name (first wins). Post-merge validation covers task/controller/resource references, presets, pre-tasks, setting sections, and duplicate case/input/hotkey names. `scan_select` expands `scan_dir` + `scan_filter` into in-memory cases and rescans via `/api/interface/scan-select/rescan` under `interface_lock`.
- **Override precedence** (`PipelineOverrideService`): task base `pipeline_override`, then deep-merge `global_option` → selected resource options → active controller options → task options. Recursive cases, controller/resource applicability, input coercion, placeholder substitution, and `scan_select` attachment happen here. Hotkeys use controller-specific conversion in `backend/maa_worker/hotkey.py`. Omitted option `type` defaults to `select` and is serialized explicitly for the frontend.
- **Global values**: `interface.setting` only groups the settings UI. Its values and PI `pretask.option` values (with nested cases, edited inline in `PreTaskList.vue`) persist in `settings.json.globalOptionValues`. Only `global_option` members enter pipeline overrides.
- **Path inputs**: `input_type` `file`/`directory` renders an editable box plus a project-dir tree picker (`ProjectPathPickerDialog.vue`, lazy `/api/file/list`, with the project dir itself selectable as `.`); it is the browser-safe fallback for the PI system dialog and works the same over LAN. The loader rejects path inputs whose `pipeline_type` is not `string`. Picked values are stored project-relative; `InputCase.runtime_value` turns relative values into absolute `PROJECT_DIR` paths for pipeline overrides and pretask option payloads (agents' cwd is the app root, which differs from the project dir in source runs). Absolute (host-OS form) or empty values pass through unchanged and nothing requires the path to exist.
- **Pre-task enabled state**: `settings.json.pretaskEnabled`, keyed by `name` or else the compact JSON array `[exec, ...args]` (byte-identical between `Pretask.key` and frontend `pretaskKey`; duplicate keys rejected; missing = enabled). Rewritten when switching/resetting to a preset that declares `pretask` (unlisted entries become unchecked) or on load while the map is empty, so `App.vue` loads settings before `loadConfig()`. Execution reads saved settings, so manual start awaits `flushSaves` (re-waits the queue after its own retry) and aborts if saving still fails. `preset.controller` only filters/disables presets in the UI.
- **Task config** (`config/task_config.json`): `selectedPreset` plus per-preset `tasks`/`taskOptions`/`preTasks`. `backend/models/task_config.py` seeds missing presets, filters invalid task names preserving order and repeats, normalizes option values, and never appends new tasks to an existing queue.
- **Interface text (`$key`)**: `backend/maa_worker/interface_text.py` and frontend `utils/interface/content.ts` `resolveInterfaceText` resolve against the current UI language (`settings.json.ui.language` mapped to `interface.languages` keys like `en_us`), flat key first, then dotted path. Missing keys yield `None`/caller fallback, never literal `$key`; `resolve_tree` keeps original values for PI env payloads. Used for `PI_CLIENT_LANGUAGE`, `PI_CONTROLLER`/`PI_RESOURCE`, focus templates, notification app name, and pretask labels. `ui.language` is authoritative: the settings store applies it to vue-i18n and the `locale` cache after load/reset and only backfills from the cache when the backend value is `null`.
- **Custom devices**: addresses validated/canonicalized by `backend/models/device_address.py` + `validation/device.ts` (strict for custom, lenient Adb for scanned), stored in `panel.customDevices`; scan wins on duplicate identity.

### Events

- **Thread→asyncio bridge**: MAA runs on threads; `EventService._publish_event` pushes `RealtimeEvent` into the `AppState` singleton's `message_conn` (`queue.SimpleQueue`, 0.05s throttle). `log_monitor` polls every 100ms, appends non-modal events to bounded history, and fans out via `LogBroadcaster` to SSE `/api/logs`; if it dies, SSE goes silent. Event names (`backend/models/api.py`): `log`, `focus.display`, `focus.modal`, `task.started`, `task.completed`, `task.failed`, `notification.test`. Adding one requires updating that model, `front/src/types/realtimeModel.ts`, and listeners in `front/src/app/main.ts`, plus the dispatcher/SSE normalization if payload or effects change.
- **Sink→Focus**: built-in Resource/Controller/Tasker/Context sinks flow `SinkHandler` → `UnifiedFocusResolver` → `FocusEventProcessor`. Non-blocking channels (`log`/`toast`/`notification`/`dialog`) map to `focus.display` `display`/`notify`; `notification` can also trigger system notifications and external channels, with policy re-read from persisted `settings.json`, not `AppState.settings`. Agent-embedded EventSink subclasses are AST-detected and registered directly on MAA objects, bypassing the focus processor; their modules still import against the temporary `maa.agent` stub.
- **External notification channels**: `settings.json.notification.channels` is a `type`-discriminated list (`backend/models/notification.py`, mirrored by `front/src/components/settings/notification/channels.ts`). `backend/services/notification.py` instantiates apprise plugin classes directly, never apprise URLs: apprise discovers URL schemas by listing its plugin directory, which does not exist in the Nuitka build. DingTalk/Feishu/WeCom robots and the custom webhook are local `NotifyBase` subclasses because apprise's versions only check HTTP status (these APIs return 200 with an error code) and its Feishu lacks signing. The apprise `app_id` stays ASCII `MWU` because plugins put it in HTTP/mail headers. `EventService` sends on a daemon thread so sink callbacks and stop never wait on network timeouts; per-channel config and send failures are logged (request errors as status code or exception type only, since URLs carry tokens), never raised.
- **Blocking modals**: `FocusEventProcessor` registers a pending modal and blocks the sink callback until `POST /api/focus/{id}/confirm` or cancellation. `focus.modal` carries the full pending snapshot in `focus_modals`, bypasses history, and is replayed on SSE connect; its empty `message` is intentional and must pass the frontend shape check. `TaskService.stop()` sets `stop_flag` under the focus lock and releases pending modals; later modals are ignored. Keep that ordering so stop never leaves a callback waiting. This is a confirmation gate, not a pause/resume API.

### Scheduling

- **APScheduler**: APScheduler 3 `AsyncIOScheduler` + `SQLAlchemyJobStore`. `scheduled_job_fired` must stay module-level in `backend/scheduler/manager.py` (the jobstore persists function references); `_CALLBACK_STATE` binds runtime state in `initialize()`. Conflict codes: `busy_manual`/`busy_scheduled`/`update_in_progress`; manual rejections write no history, scheduled skips do. SQLite work uses `asyncio.to_thread`, finalization is shielded, pre-start cancellation has separate compensation, and `scheduler_executions` is trimmed to 1000 rows.
- **Native wakeup**: `SystemScheduler` is a stateless desired-set adapter over Windows `schtasks`, macOS `launchctl`, Linux `crontab`, or `NullBackend` (`supports_native=False`), using list-argument subprocesses and platform quoting. Converge re-registers enabled tasks, removes orphans, isolates per-task failures, and reports a failed listing as `ConvergeReport.list_error`; backends raise on unknown listing errors instead of returning empty. Create registers natively first and unregisters if APS fails; update changes APS first, then native (failures raise; startup converge repairs drift); delete/pause/resume return `False` only for a missing job. Startup degrades per-task registration failures to in-app dispatch. Cold start with `--scheduled-task <id>` delegates to a running instance over the loopback internal endpoint, else submits with origin `native`.
- **Cron subset**: `PortableCronStr` wraps `pydantic-extra-types.CronStr`: 5 fields, single value or `*`, concrete minute, no day+DOW combination; the same model feeds APScheduler and OS conversion. Frontend `validation/cron.ts` mirrors and canonicalizes it and gates the wakeup switch; both share `tests/fixtures/validation_contract.json`. Native wakeup also blocks conservative same-minute conflicts on create/update.

### Update, version, telemetry

- **Update**: checks use `interface.version`, prefer MirrorChyan, fall back to GitHub, and may supplement MirrorChyan metadata with a GitHub download URL. Downloads apply the configured proxy to non-MirrorChyan sources and verify SHA-256 when supplied. `update_in_progress` gates admission once download starts; download/outer failures clear it immediately, updater-loop termination clears it in `finally`, and successful installation shuts the old process down. A daemon thread runs the updater loop; `mwu-updater` handles guarded extraction, exit-code-10 self-update, `changes.json` incremental diff, webhook shutdown, lock wait, install, and detached restart.
- **Version**: root `version` is a gitignored local artifact that may be absent or stale. Release packaging writes `github.ref_name` to `build/main.dist/version`; `agent_service.build_pi_env()` reads it for `PI_CLIENT_VERSION` (empty if missing) and passes the app root (holding `config/`/`debug/`) as `PI_USER_DATA_DIR`.
- **Telemetry**: `backend/services/telemetry.py` is the only `sentry_sdk` importer. It initializes only if `interface.telemetry.sentry.dsn` is set, the backend is Nuitka-compiled (`__compiled__`, or `MWU_TELEMETRY_FORCE=1`), the resource version is not a debug version, and `settings.json.telemetry.helpImproveSoftware` (default true) allows; `/api/settings` POST applies consent immediately, and init failures are logged and leave it disabled. `_complete_run` builds one `RunTrace` per run and calls `finish()` after history, before the slot-clearing segment; `run_process` adds per-task spans with redacted option summaries. Failed runs (including unsuccessful MAA tasks) send one error event tagged `failure.stage`; task-stage failures attach `on_error` screenshots and the raw `maafw.log` tail, while `pretask`/`device` failures send only the stage name because their text contains commands or addresses. Focus templates with `trace` (default only `Node.PipelineNode.Failed`) add `mwu.node` spans. Python logging is breadcrumb-only, excluding `backend.maa_worker.execution`.

### Frontend

- `app/main.ts` installs Pinia/router/i18n, anchors naive-ui styles, and registers SSE listeners before mount. `App.vue` provides NConfigProvider + NMessageProvider + NDialogProvider, hosts `FeedbackBridge` (must stay under `NMessageProvider`; it registers `useMessage` into `services/feedback/message.ts`) and `FocusDialogHost`, hydrates interface/task config/settings, and owns navbar/dock/update UI. `AppMain.vue` uses `<router-view>` with `mode="out-in"`; keep the rendered component inside one keyed `<div>`, since multi-root views break later route rendering. Home is eager; tasks/routines/logs/settings are lazy.
- API modules use raw `fetch()` and own endpoint-specific mapping and feedback; `services/api/core/types.ts` only shares envelope types (no central client/interceptor). `SSEClient` does a minimal payload shape check and relies on native `EventSource` reconnection, reopening only after the browser reports `CLOSED`.
- Stores: settings patches local state and serializes whole-document saves through a queue; task-config owns queue/order/options/presets with debounced persistence, trusts server-normalized config, and never enables persistence after a failed load; `focus/focus.ts` owns the dialog queue and modal snapshots, with blocking modals taking priority.
- `stopActiveAndRestart` (`stores/device/deviceConnection.ts`) stops, waits (bounded) for `TaskRunning` to clear, then retries `busy_manual` every 500ms up to 60s, because `/api/stop` returns before `active_run` clears and a refreshed page never sees `TaskRunning`. It never retries `busy_scheduled`/`update_in_progress`, shares one in-flight sequence, and is cancelled by `cleanup()`.
- `TaskSelectList` keeps `:delay="120" :delay-on-touch-only="true"` for touch drag sorting. `SchedulerTaskDialog`'s wakeup switch is enabled only for eligible cron values.
- Logs view: the download button fetches the `/api/logs/export` zip (`backend/services/log_export.py`: SSE history as `mwu.log`, tails of `debug/*.log` and `updater.log` cut at a line start, newest `debug/on_error`/`debug/vision` images under a size budget, skipping ones that no longer fit). Masked plaintext `password` values, including JSON-escaped forms, come from settings, all presets, scheduled jobs, and `AppState.run_secrets` (values runs in this process actually used, added by `_complete_run` before pre-tasks, so unsaved or since-changed passwords stay masked until restart). Export snapshots text logs before collecting passwords, so a run starting mid-export cannot add unmasked passwords. Screenshot save/copy uses a lossless PNG `/api/device/screenshot` at the controller's capture size (the same frame tasks and the preview see, not necessarily the raw device resolution; switching to raw size would change the shared controller option mid-run); clipboard image copy needs a secure context (localhost/HTTPS), so plain-HTTP LAN shows an error instead. Tap mode maps clicks on the `object-contain` preview to screenshot pixels (`utils/containedPoint.ts`) and posts `/api/device/click`; a failed click on a dead connection releases the lock like a failed screencap.

## Commands

- `uv sync` (Python from `.python-version`, >=3.13); `uv run main.py` starts the server and opens the UI (no `--reload`); `uv run pytest tests/ -q`; `uv run ruff check .` and `uv run ruff format .` (rules in `pyproject.toml`).
- `cd front && pnpm install --frozen-lockfile` (pnpm 11, Node >=24.13.0); `pnpm dev` (Vite, `/api` proxied to `localhost:5566`), `pnpm build` (to `../page`), `pnpm lint` (oxlint + eslint), `pnpm format` (oxfmt), `pnpm type-check` (`vue-tsc --noEmit`), `pnpm test:run` (Vitest, jsdom + MSW).
- `cd updater && go build`.
- `uv sync --locked --group build` installs Nuitka deps; build commands are in `.github/workflows/build.yml` and `README.md`.
- `uvx pre-commit run --all-files` runs lockfile/format hooks (frontend deps must be installed); commit hooks format only staged files.

## Coding Style

- One cohesive responsibility per file; prefer under ~800 lines, split by responsibility, not line count, and avoid many tiny modules. Reuse domain boundaries, keep public APIs small, avoid circular deps and unrelated refactors.
- Python 3.13+, snake_case, modern syntax (`list[T]`, `X | None`, `type` aliases); no version checks, shims, or backports.
- Frontend: 2-space, LF, 100 columns, double quotes, no semicolons (`front/.editorconfig`, `front/.oxfmtrc.json`); Tailwind v4 alongside naive-ui. Lint forbids `as` casts, enums, `else`, and `try/catch`; use literal unions, early returns, and `utils/tryCatch.ts`. It also forbids raw `fetch` outside `services/api` (and `utils/interface/content.ts`), `useMessage` outside `FeedbackBridge.vue`, and `@/stores` barrel imports inside `stores/` (cycles).
- Lint split: `.oxlintrc.json` owns every rule oxlint implements (type-aware for `.ts`); `eslint.config.ts` disables those via `eslint-plugin-oxlint` but keeps typed rules for `.vue` scripts, which tsgolint does not read, and adds Vue/vue-i18n/style rules. Add a rule to oxlint when it exists there. Inside `withVueTs()`, scope type-aware rule configs with `files`, never `ignores` (it drops `ignores` when relocating them).
- Vue APIs and naive-ui template components are auto-imported; import explicitly only values used outside templates (e.g. `h(NIcon)`, naive-ui composables, theme/locale) and types. Never hand-edit `front/auto-imports.d.ts` or `front/components.d.ts`.
- User-facing text goes in mirrored zh-CN/en-US i18n dictionaries.
- Respect pnpm `catalog:` and Python lock files. Before adding or changing usage of a third-party library, check current official docs (context7, source, official site) and verify compatibility with both runtimes.

## Testing

Backend tests live in `tests/unit/` (fixtures in `tests/conftest.py`); frontend Vitest tests are colocated in `front/src/` with shared MSW/EventSource setup in `front/src/tests/`. CI runs ruff check/format, pytest, Vitest, and type-check; frontend lint/format are local.

Keep tests minimal and behavioral: extend existing tests, add a case only for a plausible user-visible bug or a meaningful contract/boundary/state transition, and remove tests for removed behavior. Never assert source text, exact UI/log wording, call wiring, or mock forwarding, and don't chase coverage or enumerate unrealistic combinations.

Verify proportionally: backend changes get focused pytest plus `uv run main.py` or an `import main` smoke; frontend changes get build/lint/type-check, relevant Vitest, and a browser smoke in extension-free headless Chrome (`--headless=new --disable-extensions`); updater changes get `go build` plus a focused scenario. Doc-only edits need no test runs.

## Commits & PRs

Conventional Commits (`feat: ...`, `fix(scope): ...`, `build(deps): ...`, `docs: ...`; full rules in `.github/.copilot-commit-message-instructions.md`), short subjects, no trailing period. PRs describe the change, list validation, link issues, and include screenshots for visible frontend changes.

## AI Assistant Practices

- Use `task` subagents (`scout` for read-only research) for independent slices; keep the decomposition and cross-task contracts in the main agent.
- Check project memory/history before substantial changes and verify it against current code. Keep only settled decisions and durable conventions; never write intermediate status, investigation reports, or planning docs into the repo unless asked.
