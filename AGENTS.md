# Repository Guidelines

## Project Structure & Module Organization

MWU is a generic UI for `https://github.com/MaaXYZ/MaaFramework`. Backend entry is `main.py` (FastAPI routes, lifespan, SPA/static hosting); shared state is in `app_state.py`; MAA orchestration is in `maa_utils.py`; APScheduler CRUD + system-level wakeup coordination is in `scheduler_manager.py`; execution admission/history is in `maa_worker/execution.py`; OS scheduling and update helpers are in `services/`; MAA runtime services and sink/focus handling are in `maa_worker/`; Pydantic models are in `models/`; settings persistence is in `settings_io.py` with JSON5-tolerant reads through `json_utils.py`. Frontend code is under `front/src/`: `app/` (bootstrap/nav/theme/i18n/router), `views/` (5 route views), route-grouped `components/`, 6 Pinia `stores/`, `services/` (API/feedback/realtime), `validation/` (Zod mirrors of backend contracts), `types/`, and `utils/`. Vite emits static assets to `page/`; current release packaging is in `.github/workflows/`, the Go updater is in `updater/`, integration/deployment helpers are in `deploy/`, and user inputs are rooted at `resource/`, `interface.json`, and `agent/`.

## User Integration Scope

Users bring their own MaaFramework `resource/` folder, `interface.json`, and `agent/` code. Treat these as integration inputs, not MWU development targets. Improve the generic loader/runtime; do not bake in project-specific resources, tasks, or agent behavior.

## Current Architecture

- **Bootstrap and hosting**: `main.py` resolves the application root, loads and validates `interface.json` plus configured language files, owns the HTTP API, and creates the singleton runtime during FastAPI lifespan. Startup builds `MaaWorker`, realtime broadcasting, execution-history storage, `SystemScheduler`, and `SchedulerManager`; native registrations converge while APScheduler is paused, then APScheduler resumes. Uvicorn binds `0.0.0.0:5566`; browser launch and native-dispatch delegation use loopback. `/assets` serves `page/assets`, `/resource` serves the user resource tree, the SPA fallback serves `page/index.html`, and `/api/file` only serves app-root-contained paths.
- **State and service container**: `AppState` owns the queue/history broadcaster, settings, device/task/agent runtime dataclasses, active execution slot, update gate, scheduler references, native token, and shutdown state. `MaaWorker` is the composition root: one module-level CPU `Resource`, one per-runtime `Tasker` and HTTP client, five orchestration services, plus `SinkService`. Services share runtime through `worker.*_state` and may orchestrate sibling services through the worker back-reference.
- **Configuration and persistence**: `models/interface_loader.py` loads the full root interface, recursively merges restricted import fragments, rejects duplicate definitions and root escapes, expands `scan_select` cases in memory, and validates task/option/preset/controller/resource references. `models/task_config.py` normalizes per-preset snapshots and execution payloads against the loaded interface. Settings writes are atomic and preserve `panel.customDevices`; task config and APS/execution history use separate persistence paths under `config/`.
- **Execution and scheduling**: manual, in-app scheduled, and native scheduled starts all enter `maa_worker/execution.py`, which owns single-slot admission, conflict/skip statuses, device/resource preparation, task-thread launch, cancellation, and execution history. `TaskService` runs pre-tasks before MAA tasks and polls stop state during both. APScheduler persists jobs in `config/scheduler.sqlite`; the same database also holds trimmed execution history. System wakeup is a stateless desired-set adapter over Windows `schtasks`, macOS `launchctl`, Linux `crontab`, or `NullBackend`.
- **Events and notifications**: built-in MAA sinks flow through `SinkHandler` → `UnifiedFocusResolver` → `FocusEventProcessor` → `EventService`. `EventService` places closed-schema `RealtimeEvent` objects on `AppState.message_conn`; `log_monitor` appends history and broadcasts SSE on `/api/logs`. The frontend dispatcher independently applies log, toast, browser-notification, and task-running side effects. A `notification` event channel can also trigger backend system notifications and external webhook delivery; notification policy is re-read from persisted `settings.json`, not taken from the cached `AppState.settings` object.
- **Frontend application**: `front/src/app/main.ts` installs Pinia/router/i18n, registers all SSE event listeners, then mounts the provider shell in `App.vue`. `App.vue` hydrates interface, task config, and settings and owns global navigation/theme/update UI. Route views remain thin composition layers; domain behavior lives in Pinia stores, route-grouped components, API/realtime/feedback services, and shared validation/types/utils. API modules use raw `fetch()` and share response types only—there is no central client or interceptor.
- **Build and update boundary**: Vite builds `front/` into `page/`; packaged applications combine the static page, a Nuitka standalone backend, MaaAgentBinary, and the platform Go updater. Update checks prefer MirrorChyan metadata and fall back to GitHub, download with the configured source-specific proxy behavior, verify SHA-256 when supplied, gate new executions with `update_in_progress`, and hand installation/restart to `mwu-updater`.

## Build, Test, and Development Commands

- `uv sync`: install Python dependencies (Python 3.12.10, `.python-version`).
- `uv run main.py`: start FastAPI on `0.0.0.0:5566` and open the loopback UI (no `--reload`).
- `cd front && pnpm dev`: run Vite with `/api` proxy to `localhost:5566`.
- `cd front && pnpm build`: build frontend output to `../page`.
- `cd front && pnpm lint`: run oxlint + eslint.
- `cd front && pnpm format`: format with oxfmt.
- `cd front && pnpm type-check`: run `vue-tsc --noEmit`.
- `cd front && pnpm test:run`: run Vitest with jsdom + MSW.
- `uv run pytest tests/ -q`: run backend tests.
- `cd updater && go build`: build the Go updater.
- `pre-commit run --all-files`: run lockfile/format hooks.

## Coding Style & Naming Conventions

Follow module boundaries; keep backend, frontend, and updater changes scoped. Python uses `uv` and snake_case. Frontend files use TypeScript/Vue conventions, 2-space indentation, LF endings, 100-column formatting, double quotes, no semicolons per `front/.editorconfig` and `front/.oxfmtrc.json`. naive-ui components are auto-imported (unplugin `NaiveUiResolver` + `AutoImport` vue) — do not hand-import component values, keep type imports. Tailwind v4 utility classes are used alongside naive-ui (34+ vue files). Do not hand-edit generated declarations. No type assertions (no `as` casts) in frontend code. Do not add deps outside the pnpm `catalog:`/pyproject pins without verifying both runtimes.

## Testing Guidelines

There is no unified test suite. CI runs backend `uv run pytest tests/ -q` and frontend `pnpm test:run` + `pnpm type-check`; release packaging also builds the frontend. Validate the affected layer locally: backend changes run focused pytest plus `uv run main.py` or an `import main` cold-start smoke; frontend changes pass build/lint/type-check/Vitest and browser-drive the affected surface; updater changes pass `go build`. Add focused tests or smoke scripts only for observable behavior that is otherwise hard to verify. Browser verification must use an extension-free headless Chrome (`--headless=new --disable-extensions`).

## Commit & Pull Request Guidelines

Use Conventional Commits, matching history: `feat: ...`, `fix(scope): ...`, `build: ...`, `deps: ...`, or `docs: ...` (full rules in `.github/.copilot-commit-message-instructions.md`). Keep subjects short and omit trailing periods. PRs should describe the change, list validation, link issues, and include screenshots or recordings for visible frontend changes.

## Working Practices (AI Assistants)

- **Third-party libraries**: before adding a new dependency or changing usage of an existing one, query the latest official documentation (context7 docs, library source, official site) — never assume API facts from memory. Version pins in this repo are locked (pnpm catalog, pyproject/uv.lock); verify any new dependency against both runtimes before introducing it.
- **Subagents**: use `task` subagents (read-only `scout` for investigation) for independent work slices — multi-file changes, refactors, research — to keep the main agent's context concise. Own the decomposition and cross-task contracts; don't delegate the top-level plan.
- **Memory**: before writing code, `recall`/`reflect` to quickly load current codebase state and conventions; after finishing work, `retain` durable facts (decisions, changes, pitfalls) so future sessions stay current.

## Agent-Specific Notes

Preserve the backend/frontend API contract and keep `interface.json` path handling rooted at the app directory (path containment enforced in `models/interface_loader.py`). `maa_worker/agent_loader.py` contains the dynamic-loading "magic" that imports and registers code from the user's `agent/` folder. Its custom decorator parsing is string-pattern based and can silently fail if expected decorator forms change.

### Key Architecture Constraints (Non-Obvious)

These are hard-won learnings from previous sessions — do not reintroduce these issues:

- **MaaWorker is a DI container**, not a service. It exposes the module-level Resource singleton, a per-runtime Tasker/HTTP client, runtime state aliases, five orchestration services (`events`, `device`, `pipeline`, `agents`, `tasks`), and `SinkService`; every service gets a back-reference to the worker. Shared state is read/written through `worker.*_state`, while orchestration may call sibling services through `worker.<service>`. Runtime state dataclasses live in `app_state.py` (`DeviceRuntimeState`/`TaskRuntimeState`/`AgentRuntimeState`), not a separate runtime module.
- **Thread→asyncio bridge**: Worker runs MAA on threads, `EventService._publish_event` pushes `RealtimeEvent` to `app_state.message_conn` (`queue.SimpleQueue`) with a 0.05s throttle. The `log_monitor` asyncio task polls every 100ms → normalizes → appends to `history_message` deque (maxlen 2000) → `LogBroadcaster` fan-out to SSE clients (`/api/logs`). **If log_monitor dies, SSE goes silent.** `focus.interaction` events are filtered out of history replay but broadcast live. RealtimeEventName is closed: `log`, `focus.display`, `focus.interaction`, `task.started`, `task.completed`, `task.failed`, `notification.test` — adding one requires updating the backend literal, `front/src/types/realtimeModel.ts`, and the listener list in `front/src/app/main.ts`; update `front/src/services/realtime/dispatcher.ts` only for type-specific side effects.
- **Sink→Focus pipeline**: built-in MWU Resource/Controller/Tasker/Context sinks flow through `SinkHandler` → `UnifiedFocusResolver` → `FocusEventProcessor`. The internal `FocusDisplayEvent.display_channels` are serialized as `RealtimeEvent.display` plus `notify` entries when `focus.display` is emitted. Agent-embedded EventSink subclasses are detected by AST and registered directly on MAA objects, so they bypass the MWU focus processor; their modules still import against the temporary `maa.agent` stub during black-magic loading.
- **`configuration_locked` is a one-way ratchet**: set when `set_resource()` succeeds after connect. Once locked, `connect()` / `set_resource()` refuse. Only `reset_connection_state()` (called on connection failure/liveness loss via `/api/device/state`) releases it.
- **`stop_flag` is polled both between tasks AND during each task**: `TaskService.stop()` is the unified stop path — set stop_flag, submit `post_stop()` once (no wait), wake pending focus modals, then join the worker thread (30s cap). Inside `run_process()`, the inner `while not t.done: sleep(0.5); if stop_flag: return` loop is how mid-pipeline abort works; pre-tasks also poll it.
- **Decorator regex is fragile**: Only `@AgentServer.custom_action("...")` / `@AgentServer.custom_recognition("...")` with **double quotes** matches. Single quotes → silent failure. Class def must be on the line immediately after the decorator. The `_BlackMagicAgentServer` stub keeps library in client mode during in-process import.
- **Agent startup is lazy and one-shot**: `TaskService.start()` calls `AgentService.ensure_started_once()` before launching the task thread. Embedded Python agents use the custom module finder, `deps/` precedence, black-magic stub, regex/AST registration, and direct in-process instances; external agents use `AgentClient` plus subprocesses. `started_once` is a ratchet even after failure, and previously connected external processes accumulated earlier in the batch are cleaned up before the aggregate error is retained.
- **Pipeline override precedence is fixed**: `PipelineOverrideService` starts from the task's base `pipeline_override`, then deep-merges option groups in `global_option` → selected resource options → active controller options → task options order. Recursive case options, controller/resource applicability, input coercion, placeholder substitution, and `scan_select` attachment all happen here.
- **Frontend uses raw `fetch()`**, not axios. API modules own their endpoint-specific response mapping and feedback; `services/api/core/types.ts` only shares envelope types, with no central interceptor/client. Toast bridge: `FeedbackBridge.vue` registers naive-ui `useMessage` into `services/feedback/message.ts` and must remain under `NMessageProvider`.
- **`version` file is stale in dev** (says `v0.11.0` vs `pyproject.toml` `0.17.0`). CI rewrites it with `github.ref_name` (`build.yml`). `agent_service.build_pi_env()` reads it directly — mismatch is expected in dev.
- **Scheduler execution model**: APScheduler 3 `AsyncIOScheduler` + `SQLAlchemyJobStore` (`config/scheduler.sqlite`), callback is module-level `scheduled_job_fired` because the jobstore persists function references; runtime state is bound through `_CALLBACK_STATE` during `initialize()`. `submit_manual`/`submit_scheduled` use a single event-loop-owned `state.active_run` slot, then `_complete_run` prepares device/resource with retry, starts the task thread, polls completion, writes history, and clears the slot. Conflict codes are `busy_manual`/`busy_scheduled`/`update_in_progress`. SQLite work is offloaded with `asyncio.to_thread`: admission/skip writes are awaited, finalization is shielded, and only pre-start cancellation compensation is scheduled fire-and-forget. `scheduler_executions` is trimmed to 1000 rows.
- **Event-order quirk → frontend retry**: `TaskService.run_process()` emits task terminal events before `_complete_run` observes `running=False`, finishes history, and clears `active_run`. The frontend therefore retries only `busy_manual` conflicts (`stopActiveAndRestart` in `stores/device/deviceConnection.ts`: 500ms interval, 60s cap) and must not retry `busy_scheduled` or `update_in_progress`.
- **System-level wakeup (OS native scheduling)**: `SystemScheduler` is stateless and converges to the desired set by re-registering enabled wakeup tasks, unregistering orphans, and isolating per-task failures. Backends are Windows `schtasks`, macOS `launchctl`, Linux `crontab`, or `NullBackend` (`supports_native=False`), using list-argument subprocesses and platform quoting. Create/update perform native registration first and compensate around APS failure; pause/resume/delete also touch native state before APS but are not fully transactional. Startup degrades per-task registration failures to app-internal dispatch. Cold start uses `--scheduled-task <id>`; a second process delegates to the running instance through the token-protected internal endpoint, otherwise it submits with origin `native`.
- **Cron validation is a single strict subset**: `PortableCronStr` composes `pydantic-extra-types.CronStr` with project before/after validators: 5 fields, single value or `*`, concrete minute, and no day+DOW combination. The same model feeds APScheduler and OS conversion. Frontend `validation/cron.ts` mirrors and canonicalizes the contract, gates the wakeup switch, and shares corpus cases with backend tests. Native wakeup also blocks conservative same-minute conflicts at create/update.
- **interface.json loader**: the root file uses the full interface schema; recursively imported fragments may only contain `task`/`option`/`preset`/`import`. Import paths resolve from the app root, duplicate task entries/names/options/presets fail loudly, and absolute/parent/drive/UNC escapes are rejected. `scan_select` expands `scan_dir` + `scan_filter` into in-memory `cases` and can rescan through `/api/interface/scan-select/rescan`; task context references and presets are validated after merge.
- **Custom devices**: user-entered addresses are validated/canonicalized (`models/device_address.py` + `validation/device.ts`, strict for custom, lenient Adb for scanned) and persisted in `settings.json` `panel.customDevices`; `settings_io.write_settings_preserving_custom_devices` force-preserves them on `/api/settings` POST (atomic tmp+fsync+replace under `SETTINGS_LOCK`). Scan wins on duplicate identity.
- **Task config/presets**: `config/task_config.json` stores `selectedPreset` + per-preset snapshots (`taskOrder`/`taskChecked`/`taskOptions`/`preTasks`); backend `normalize_task_config` re-seeds interface presets, appends new tasks to persisted order, and normalizes options against the interface on load/save. Pre-tasks (`PreTaskCommand`: command/enabled/timeout, shell execution with output capture + stop/terminate handling) run before the task list in `run_process`; failure aborts the run.
- **Update flow**: `update_in_progress` gates all task admission once package download starts. Check prefers MirrorChyan API (CDK) then GitHub; download verifies SHA-256 when present; `mwu-updater` handles guarded extraction, exit-code-10 self-update, `changes.json` incremental diff, webhook shutdown, lock wait, apply, and restart from a background thread. Download/outer failures clear the gate immediately; updater-loop termination clears it in `finally`, while successful installation shuts down the process.

## Frontend layout

- `app/`: `main.ts` installs Pinia/router/i18n, anchors naive-ui styles, and registers the six closed SSE event names before mount. `App.vue` provides NConfigProvider + NMessageProvider + NDialogProvider + FeedbackBridge, hydrates interface/task config/settings, and owns navbar/dock/update UI. `AppMain.vue` uses `<router-view>` with `mode="out-in"`; the rendered component MUST remain wrapped in one keyed `<div>` because multi-root views otherwise break later route rendering. `router/` defines home eagerly and lazy-loads tasks/routines/logs/settings; `i18n/` mirrors zh-CN/en-US keys; `theme.ts` maps light/dark overrides and naive locales.
- `views/`: thin composition per route — HomeView (device/resource selectors + stats + presets + routine health), TasksView (task list w/ PreTaskList + TaskSelectList, start/stop, StartConflictDialog sibling root), RoutinesView (scheduler tabs: task list + execution history), LogsView (live preview stream + log panel), SettingsView (5 sections; desktop NMenu / mobile NTabs).
- `components/` grouped by route: `panel/task/` (TaskSelectList drag-sortable with `:delay="120" :delay-on-touch-only="true"`, TaskOptionPanel/OptionItem recursive option editors incl. scan_select rescan, PreTask*, TaskSettingsDrawer mobile bottom drawer, TaskDescriptionCard markdown via marked+DOMPurify), `routines/` (SchedulerTaskDialog = 3 composables `useSchedulerTaskForm`/`useSchedulerTaskSave`/`useTaskEnvironment` + SectionNav/TriggerType/ContentTabs; wakeup switch only enabled when cron eligible), `settings/sections/` + `dialogs/UpdateDialog`, `tasks/StartConflictDialog`.
- `stores/`: device (connection + `StartTask` + conflict retry), interface (task/option/preset getters, compatibility filter, scan_select rescan), panel/session (index), scheduler (CRUD), settings (optimistic update with rollback), task-config (task list/order/options/presets, debounced save).
- `services/`: API modules cover task/device/interface/resource/settings/task-config/scheduler/update/notification endpoints and re-export through `services/api/index.ts`; `core/types.ts` contains shared envelopes, not request machinery. Feedback is the queued naive-ui message bridge. Realtime is `SSEClient` with payload normalization and exponential-backoff reconnect plus a dispatcher for log/toast/browser-notification and `TaskRunning` side effects.
