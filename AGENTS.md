# Repository Guidelines

## Project Positioning & Design Boundaries

MWU is a generic MaaFramework UI for one person's own use, running locally or on that person's trusted LAN. It is not a public Internet service, a multi-user platform, or a multi-tenant system. The default design assumes exactly one user; access from another device on the LAN does not change that scope.

Write the simplest correct implementation for the current use case. Do not overengineer or add speculative defensive code. Do not introduce account systems, permission hierarchies, tenant isolation, distributed coordination, generic frameworks, or compatibility layers for hypothetical future requirements. Add an abstraction only when current code has a concrete need for it.

Keep safeguards that address real failure modes: malformed configuration, unsafe file paths, interrupted writes, task cancellation, subprocess cleanup, and overlapping manual/scheduled execution. One user does not eliminate background tasks or worker threads. Validate at the relevant boundary, make failures visible, and avoid repeated validation of already-normalized internal data, blanket exception suppression, silent fallbacks, or retries without a demonstrated need.

Keep test code as small as practical. Cover observable behavior and plausible regressions rather than maximizing test counts, coverage percentages, or exhaustive combinations. Verification should be proportional to the changed behavior; documentation-only edits do not need application test runs.

## Project Structure & Module Organization

MWU is a generic UI for `https://github.com/MaaXYZ/MaaFramework`. Backend entry is `main.py` (FastAPI routes, lifespan, SPA/static hosting); shared runtime state is in `app_state.py`; `maa_utils.py` composes the MAA runtime. `scheduler_manager.py` owns APScheduler CRUD and native wakeup coordination; `maa_worker/execution.py` owns admission, preparation, cancellation, and execution history. `maa_worker/pretask_service.py` runs interface-defined and user-command pre-tasks; other MAA services and sink/focus handling also live in `maa_worker/`. OS scheduling and update helpers are in `services/`; Pydantic models and interface/task-config normalization are in `models/`; atomic settings persistence is in `settings_io.py`, with JSON5-tolerant reads through `json_utils.py`.

Frontend code is under `front/src/`: `app/` (bootstrap/nav/theme/i18n/router), thin route `views/`, domain-grouped and shared `components/`, domain Pinia `stores/`, `services/` (API/feedback/realtime), `validation/` (frontend contract validation), `types/`, and `utils/`. Vite emits static assets to `page/`. MWU's release packaging lives in `.github/workflows/`, and the Go updater is in `updater/`. `deploy/` contains the downstream-project packaging template and resource/dependency scripts that consume an MWU release, not MWU's own release pipeline.

## User Integration Scope

Users bring their own MaaFramework `resource/` folder, `interface.json`, and `agent/` code. Treat these as integration inputs, not MWU development targets. Improve the generic loader/runtime; do not bake in project-specific resources, tasks, or agent behavior.

## Current Architecture

- **Bootstrap and hosting**: `main.py` resolves the application root, loads and validates `interface.json` plus configured language files, owns the HTTP API, and creates the singleton runtime during FastAPI lifespan. Startup builds `MaaWorker`, realtime broadcasting, execution-history storage, `SystemScheduler`, and `SchedulerManager`; native registrations converge while APScheduler is paused, then APScheduler resumes. Uvicorn binds `0.0.0.0:5566`; browser launch and native-dispatch delegation use loopback. `/assets` serves `page/assets`, `/resource` serves the user resource tree, the SPA fallback serves `page/index.html`, and `/api/file` only serves app-root-contained paths.
- **State and service container**: `AppState` owns the queue/history broadcaster, settings, device/task/agent/focus runtime state, active execution slot and coroutine, update gate/status, scheduler references, and shutdown state. `MaaWorker` is the composition root: one module-level CPU `Resource`, one per-runtime `Tasker` and HTTP client, runtime services, and `SinkService`. Services share runtime through `worker.*_state` and may orchestrate sibling services through the worker back-reference.
- **Configuration and persistence**: `models/interface_loader.py` loads the full root interface, merges restricted import fragments, rejects duplicate task/preset definitions and root escapes, expands `scan_select` cases in memory, and validates task/option/preset/pretask/setting references. `models/task_config.py` normalizes per-preset snapshots, global option values, and execution payloads against the interface. Settings writes are atomic and preserve `panel.customDevices`; option `input` fields marked `password` are Fernet-encrypted at rest by `secret_store.py` (key in the per-user data directory) in `settings.json`, `task_config.json`, and APS job kwargs, and stay plaintext in memory and API responses; task config and APS/execution history have separate persistence paths under `config/`. Interface-defined settings values live in `settings.json.globalOptionValues`.
- **Execution and scheduling**: manual, in-app scheduled, and native scheduled starts all enter `maa_worker/execution.py`. After single-slot admission and payload normalization, `_complete_run` runs `PretaskService` before device/resource preparation, then starts `TaskService`, records history, and clears the slot. Both pre-tasks and MAA tasks honor stop requests. APScheduler jobs and trimmed execution history share `config/scheduler.sqlite`. System wakeup is a stateless desired-set adapter over Windows `schtasks`, macOS `launchctl`, Linux `crontab`, or `NullBackend`.
- **Events and notifications**: built-in MAA sinks flow through `SinkHandler` → `UnifiedFocusResolver` → `FocusEventProcessor`. Ordinary focus events go through `EventService`; blocking confirmation modals enqueue separate `focus.modal` snapshots. `log_monitor` broadcasts SSE on `/api/logs` and appends non-modal events to history. The frontend dispatcher applies log, toast, browser-notification, focus-dialog/modal, and task-running effects. The `notification` display channel can also trigger backend system notifications and external webhooks; notification policy is re-read from persisted `settings.json`, not cached `AppState.settings`.
- **Frontend application**: `front/src/app/main.ts` installs Pinia/router/i18n and registers SSE listeners before mounting the provider shell. `App.vue` hydrates interface/task config/settings and hosts global navigation/theme/update UI plus `FocusDialogHost`. Route views remain thin composition layers; behavior lives in domain stores, components, API/realtime/feedback services, and shared validation/types/utils. API modules use raw `fetch()` and share response types only; there is no central client or interceptor.
- **Build and update boundary**: Vite builds `front/` into `page/`; packaged applications combine the static page, a Nuitka standalone backend, MaaAgentBinary, and the platform Go updater. Update checks prefer MirrorChyan metadata and fall back to GitHub, download with the configured source-specific proxy behavior, verify SHA-256 when supplied, gate new executions with `update_in_progress`, and hand installation/restart to `mwu-updater`.
- **Anonymous telemetry**: `services/telemetry.py` is the only module importing `sentry_sdk`. It initializes only when `interface.telemetry.sentry.dsn` is set, the backend is Nuitka-compiled (`__compiled__`; `MWU_TELEMETRY_FORCE=1` overrides for testing), the resource version is not a debug version, and `settings.json.telemetry.helpImproveSoftware` (default true) allows it; `/api/settings` POST applies consent immediately, and initialization failures are logged and leave telemetry disabled. `_complete_run` builds one `RunTrace` per run and calls `finish()` after history is written and before the no-await slot-clearing segment; `run_process` records per-task spans with redacted option summaries. Failed runs, including runs where a MAA task returned unsuccessful, report one error event tagged `failure.stage`, with `on_error` screenshots and the raw `maafw.log` tail for task-stage failures; `pretask`/`device` failures send only the stage name because their text carries commands or device addresses. Focus templates with `trace` (default: only `Node.PipelineNode.Failed`) add `mwu.node` spans with node name and task id to the active run. Python logging is breadcrumb-only, excluding `maa_worker.execution`.

## Build, Test, and Development Commands

- `uv sync`: install Python dependencies using `.python-version` (currently 3.13.15; `pyproject.toml` requires Python >=3.13).
- `uv run main.py`: start FastAPI on `0.0.0.0:5566` and open the loopback UI (no `--reload`).
- `cd front && pnpm install --frozen-lockfile`: install frontend dependencies; use pnpm 11 and Node >=24.13.0, matching the package requirement and CI major versions.
- `cd front && pnpm dev`: run Vite with `/api` proxy to `localhost:5566`.
- `cd front && pnpm build`: build frontend output to `../page`.
- `cd front && pnpm lint`: run oxlint + eslint.
- `cd front && pnpm format`: format with oxfmt.
- `cd front && pnpm type-check`: run `vue-tsc --noEmit`.
- `cd front && pnpm test:run`: run Vitest with jsdom + MSW.
- `uv run pytest tests/ -q`: run backend tests.
- `cd updater && go build`: build the Go updater.
- `uv sync --locked --group build`: install the Nuitka packaging dependencies; use the platform build commands in `.github/workflows/build.yml` or the local build instructions in `README.md`.
- `uvx pre-commit run --all-files`: run lockfile and formatting hooks; frontend dependencies must already be installed. Normal commit hooks format only the passed Python/frontend files, not the entire tree.

## Coding Style & Naming Conventions

Keep each source file focused on one cohesive responsibility. Prefer files below roughly 800 lines, but split by responsibility rather than line count and avoid creating many tiny modules. Reuse the existing domain boundaries, keep public APIs small, and avoid circular dependencies or unrelated refactors. Correctness and clear ownership take precedence over mechanical size targets.

Use `uv` for Python and `pnpm` for the frontend. Python uses snake_case.

Python code targets Python 3.13 and newer and must use modern syntax supported by the Python 3.13 baseline. Do not choose legacy syntax or introduce version checks, compatibility shims, or backports solely to support older Python releases. Prefer built-in generics (`list[T]`, `dict[K, V]`), union syntax (`X | Y`, `T | None`), and `type` aliases over equivalent legacy `typing` forms.

Frontend files use TypeScript/Vue conventions, 2-space indentation, LF endings, 100-column formatting, double quotes, and no semicolons per `front/.editorconfig` and `front/.oxfmtrc.json`. Tailwind v4 utilities are used alongside naive-ui.

Vue APIs and naive-ui template components are auto-imported by Vite plugins. Do not add redundant component imports for templates; explicitly import component values used by render functions such as `h(NIcon)`, naive-ui composables, and theme/locale values. Keep type imports explicit. Do not hand-edit generated `front/auto-imports.d.ts` or `front/components.d.ts`.

Frontend lint rules prohibit type assertions (`as` casts), TypeScript enums, `else` branches, and `try/catch`; use literal unions, early returns, and `utils/tryCatch.ts`. Keep user-facing Vue text in the mirrored zh-CN/en-US i18n dictionaries. Respect pnpm `catalog:` entries and the Python dependency/lock files when changing dependencies; verify compatibility with the affected runtimes.

## Testing Guidelines

Backend pytest tests live under `tests/unit/`, with shared fixtures in `tests/conftest.py`. Frontend Vitest tests are colocated under `front/src/`, using jsdom and the shared MSW/EventSource setup in `front/src/tests/`. Backend and frontend cron validation share `tests/fixtures/validation_contract.json`. The test workflow runs backend pytest plus frontend Vitest/type-check; the release workflow builds the frontend and packages the application. Lint and formatting are separate local checks.

Keep permanent tests minimal and behavior-focused. Prefer extending an existing relevant test over adding a new suite or fixture framework. Add a regression case only when it catches a plausible user-visible bug or a meaningful contract, boundary, or state transition. Do not add tests merely because a file changed, chase coverage targets, enumerate unrealistic combinations, or duplicate an already-covered path. Avoid assertions about source text, exact UI/log wording, internal call wiring, or mock forwarding; remove obsolete tests when behavior is removed.

Validate the affected layer and exercise the changed behavior. For backend runtime changes, run focused pytest cases plus `uv run main.py` or an `import main` cold-start smoke as appropriate. For frontend changes, use build/lint/type-check, relevant existing Vitest cases, and a browser smoke of the affected surface. For updater changes, run `go build` and a focused scenario for the changed behavior. Do not run unrelated suites by default. Browser verification must use an extension-free headless Chrome (`--headless=new --disable-extensions`).

Use Conventional Commits: `feat: ...`, `fix(scope): ...`, `build: ...`, `build(deps): ...`, or `docs: ...` (full rules in `.github/.copilot-commit-message-instructions.md`). ## Working Practices (AI Assistants)

- **Third-party libraries**: before adding a new dependency or changing usage of an existing one, query the latest official documentation (context7 docs, library source, official site) — never assume API facts from memory. Version pins in this repo are locked (pnpm catalog, pyproject/uv.lock); verify any new dependency against both runtimes before introducing it.
- **Subagents**: use `task` subagents (read-only `scout` for investigation) for independent work slices — multi-file changes, refactors, research — to keep the main agent's context concise. Own the decomposition and cross-task contracts; don't delegate the top-level plan.
- **Project context**: consult available project memory/history before substantial changes, then verify it against current code. Retain only settled decisions and durable conventions. Do not write intermediate status, investigation reports, or temporary planning documents into the repository unless the user requests them.

## Agent-Specific Notes

Preserve the backend/frontend API contract and keep `interface.json` path handling rooted at the app directory (path containment enforced in `models/interface_loader.py`). `maa_worker/agent_loader.py` contains the dynamic-loading "magic" that imports and registers code from the user's `agent/` folder. Its custom decorator parsing is string-pattern based and can silently fail if expected decorator forms change.

### Key Architecture Constraints (Non-Obvious)

These are hard-won learnings from previous sessions — do not reintroduce these issues:

- **MaaWorker is a DI container**, not a service. It exposes the module-level Resource singleton, a per-runtime Tasker/HTTP client, state aliases, `events`, `focus`, `device`, `pipeline`, `agents`, `pretasks`, `tasks`, and `sinks`. Runtime collaborators use the worker back-reference for state and orchestration. `WorkerContext`, device/task/agent/focus state, pending modals, and `ActiveRun` live in `app_state.py`, not a separate runtime module.
- **Thread→asyncio bridge**: MAA runs on threads; `EventService._publish_event` pushes `RealtimeEvent` to `app_state.message_conn` (`queue.SimpleQueue`) with a 0.05s throttle. `log_monitor` polls every 100ms, appends non-modal events to the bounded history, and fans out through `LogBroadcaster`. If it dies, live SSE delivery goes silent. The event-name contract in `models/api.py` is `log`, `focus.display`, `focus.modal`, `task.started`, `task.completed`, `task.failed`, and `notification.test`. Adding a name requires updating that model, `front/src/types/realtimeModel.ts`, and listeners in `front/src/app/main.ts`; update the dispatcher and SSE normalization when the new payload or effects require it.
- **Sink→Focus pipeline**: built-in Resource/Controller/Tasker/Context sinks use `SinkHandler` → `UnifiedFocusResolver` → `FocusEventProcessor`. Non-blocking channels (`log`, `toast`, `notification`, `dialog`) map to `focus.display`'s `display`/`notify` fields; `modal` uses a separate state snapshot. Agent-embedded EventSink subclasses are AST-detected and registered directly on MAA objects, bypassing the MWU focus processor; their modules still import against the temporary `maa.agent` stub.
- **Blocking focus confirmation**: `FocusEventProcessor` registers a pending modal and blocks the sink callback until confirmation or cancellation. `POST /api/focus/{id}/confirm` releases that modal. `focus.modal` carries the full pending snapshot, bypasses log history, and is replayed on SSE connection. `TaskService.stop()` sets `stop_flag` under the focus lock and releases pending modals; modals arriving after stop are ignored. Preserve this ordering so stopping cannot leave a callback waiting forever. This is a pipeline confirmation gate, not a general task pause/resume API.
- **`configuration_locked` is a ratchet until reset**: set when `set_resource()` succeeds after connect; while the connection remains live, locked `connect()` / `set_resource()` calls refuse. `reset_connection_state()` releases it on connection/liveness/screencap failure and when execution must replace an incompatible connection.
- **Stop lifecycle**: `_claim_slot` resets `stop_flag` when admitting a new run; do not reset it later during preparation or task startup, which would discard a stop request. `TaskService.run_process()` polls stop before, during, and after MAA tasks; `PretaskService` polls while subprocesses run. Cancelling the execution coroutine during pre-tasks must drain the shielded pre-task future before clearing `active_run`, or a new run could reset the shared flag while old commands are still running.
- **Decorator regex is fragile**: Only `@AgentServer.custom_action("...")` / `@AgentServer.custom_recognition("...")` with **double quotes** matches. Single quotes → silent failure. Class def must be on the line immediately after the decorator. The `_BlackMagicAgentServer` stub keeps library in client mode during in-process import.
- **Agent startup is lazy and one-shot**: `TaskService.start()` calls `AgentService.ensure_started_once()` before launching the task thread. Embedded Python agents use the custom module finder, `deps/` precedence, black-magic stub, regex/AST registration, and direct in-process instances; external agents use `AgentClient` plus subprocesses. `started_once` is a ratchet even after failure, and previously connected external processes accumulated earlier in the batch are cleaned up before the aggregate error is retained.
- **Pipeline override precedence is fixed**: `PipelineOverrideService` starts from the task's base `pipeline_override`, then deep-merges option groups in `global_option` → selected resource options → active controller options → task options order. Recursive case options, controller/resource applicability, input coercion, placeholder substitution, and `scan_select` attachment all happen here.
- **Option contracts and task settings**: omitted option `type` defaults to `select` in the backend and is serialized explicitly for the frontend. Hotkey options use controller-specific conversion in `maa_worker/hotkey.py` and `pipeline_override.py`. `interface.setting` only groups the settings UI; its values persist in `settings.json.globalOptionValues`. PI `pretask.option` values (with nested case options) share `globalOptionValues` and are edited inline in `PreTaskList.vue`. Only `global_option` members enter pipeline overrides; displaying an option in a setting section or pretask alone does not make it a global override.
- **Interface text (`$key`)**: backend `maa_worker/interface_text.py` (`worker.text`) and frontend `utils/interface/content.ts` `resolveInterfaceText` resolve `$key` against the translations of the current UI language (`settings.json.ui.language`, mapped to `interface.languages` keys such as `en_us`), flat key first, then dotted path. A missing key resolves to `None` / the caller's fallback, never the literal `$key`; `resolve_tree` keeps the original value for PI env payloads. The backend uses it for `PI_CLIENT_LANGUAGE`, `PI_CONTROLLER`/`PI_RESOURCE`, focus template content, the notification app name, and pretask labels. `ui.language` is authoritative: the settings store applies it to vue-i18n and the `locale` cache after a successful load or reset, and only backfills it from the cache when the backend value is still `null`.
- **Frontend uses raw `fetch()`**, not axios. API modules own their endpoint-specific response mapping and feedback; `services/api/core/types.ts` only shares envelope types, with no central interceptor/client. Toast bridge: `FeedbackBridge.vue` registers naive-ui `useMessage` into `services/feedback/message.ts` and must remain under `NMessageProvider`.
- **Version sources differ**: the root `version` file is a gitignored local artifact and may be absent or stale. Release packaging writes `github.ref_name` to `build/main.dist/version`; `agent_service.build_pi_env()` reads `version` from the app root for `PI_CLIENT_VERSION` (empty when missing). Update checks use `interface.version`, not the local `version` file or the package metadata version.
- **Scheduler execution model**: APScheduler 3 uses `AsyncIOScheduler` + `SQLAlchemyJobStore` (`config/scheduler.sqlite`). `scheduled_job_fired` must remain module-level because the jobstore persists function references; `_CALLBACK_STATE` binds runtime state during `initialize()`. `submit_manual`/`submit_scheduled` share one event-loop-owned `active_run` slot through pre-tasks, device/resource preparation, execution, and finalization. Conflict codes are `busy_manual`/`busy_scheduled`/`update_in_progress`; manual rejections create no history row, while scheduled skips do. SQLite work uses `asyncio.to_thread`, finalization is shielded, and pre-start cancellation has separate compensation. `scheduler_executions` is trimmed to 1000 rows.
- **Terminal-event ordering**: `_complete_run` emits `task.completed`/`task.failed` only after finishing history and clearing `active_run`; `TaskService.run_process()` records status but emits no terminal events. Slot clearing and `EventService.publish_task_terminal` run in one synchronous segment with no `await` between them, so a newly admitted run's `task.started` cannot precede the old terminal event; notifications follow in a worker thread. The subject uses the run label captured at start (schedule name for scheduled runs). A start issued after the frontend sees a terminal event is therefore admitted. `stopActiveAndRestart` in `stores/device/deviceConnection.ts` stops, waits for `TaskRunning` to clear (bounded), then retries `busy_manual` every 500ms up to 60s because `/api/stop` returns before `active_run` is cleared (a refreshed page never sees `TaskRunning`); it never retries `busy_scheduled` or `update_in_progress`, shares one in-flight sequence between concurrent calls, and is cancelled by `cleanup()`.
- **System-level wakeup (OS native scheduling)**: `SystemScheduler` is stateless and converges to the desired set by re-registering enabled wakeup tasks, unregistering orphans, and isolating per-task failures; a failed listing is reported as `ConvergeReport.list_error`. Backends are Windows `schtasks`, macOS `launchctl`, Linux `crontab`, or `NullBackend` (`supports_native=False`), using list-argument subprocesses and platform quoting; every backend raises on unknown listing errors instead of treating them as empty. Create registers natively first and unregisters if APS fails. Update modifies APS first, then syncs native state; native failures raise and startup `converge` repairs drift. Delete/pause/resume return `False` only for a missing job and raise on native failures. Startup degrades per-task registration failures to app-internal dispatch. Cold start uses `--scheduled-task <id>`; a second process delegates to the running instance through the loopback internal endpoint, otherwise it submits with origin `native`.
- **Cron validation is a single strict subset**: `PortableCronStr` composes `pydantic-extra-types.CronStr` with project before/after validators: 5 fields, single value or `*`, concrete minute, and no day+DOW combination. The same model feeds APScheduler and OS conversion. Frontend `validation/cron.ts` mirrors and canonicalizes the contract, gates the wakeup switch, and shares corpus cases with backend tests. Native wakeup also blocks conservative same-minute conflicts at create/update.
- **interface.json loader**: the root file uses the full schema; imported fragments may contain only `task`/`option`/`preset`/`pretask`/`import`/`global_option`/`setting`. Import paths resolve from the app root; duplicate task names/presets and absolute/parent/drive/UNC escapes fail loudly, while a later option key overrides an earlier one and groups dedupe by name (first wins). Validation after merge checks task/controller/resource references, presets, pre-tasks, settings sections, and duplicate case/input/hotkey names. `scan_select` expands `scan_dir` + `scan_filter` into in-memory cases and rescans through `/api/interface/scan-select/rescan` under `interface_lock`.
- **Custom devices**: user-entered addresses are validated/canonicalized (`models/device_address.py` + `validation/device.ts`, strict for custom, lenient Adb for scanned) and persisted in `settings.json` `panel.customDevices`; `settings_io.write_settings_preserving_custom_devices` force-preserves them on `/api/settings` POST (atomic tmp+fsync+replace under `SETTINGS_LOCK`). Scan wins on duplicate identity.
- **Task config/presets**: `config/task_config.json` stores `selectedPreset` and per-preset snapshots (`tasks`/`taskOptions`/`preTasks`). Normalization seeds missing interface presets, filters invalid task names while preserving order and repeated entries, and normalizes option values; it does not append new tasks to an existing queue. Frontend hydration regenerates per-entry `uid` values, which are not persisted.
- **Pre-task ordering**: `_complete_run` requires at least one valid task after normalization before executing commands, then runs interface `pretask` executables with args/option payloads before user `PreTaskCommand` shell commands. This happens before device/controller preparation, or before task startup when reusing a locked connection. `PretaskService` owns output capture, timeout, stop polling, and process termination; PI pretasks have no timeout (only stop terminates them) while user commands keep their configured timeout. Failure aborts the run before MAA tasks start.
- **Task identity**: execution lists and option-map keys use unique interface `task.name` definitions, not `task.entry`. A queue may repeat a task name; those entries share one option map and execute in order, while UI selection/removal uses each entry's `uid`. `task.entry` may repeat across definitions and is resolved only when calling `tasker.post_task`. `active_run.task_name` is a display label (first task for manual runs, schedule name for scheduled runs), not a pipeline lookup key.
- **Update flow**: `update_in_progress` gates task admission once package download starts. Checks use MirrorChyan when configured, fall back to GitHub on failure, and can supplement MirrorChyan metadata with a GitHub download URL. Downloads apply the configured proxy to non-MirrorChyan sources and verify SHA-256 when supplied. A backend daemon thread runs the updater loop; `mwu-updater` handles guarded extraction, exit-code-10 self-update, `changes.json` incremental diff, webhook shutdown, lock wait, installation, and detached app restart. Download/outer failures clear the gate immediately; updater-loop termination clears it in `finally`, while successful installation shuts down the old process.

## Frontend layout

- `app/`: `main.ts` installs Pinia/router/i18n, anchors naive-ui styles, and registers the closed SSE event names before mount. `App.vue` provides NConfigProvider + NMessageProvider + NDialogProvider, with FeedbackBridge and FocusDialogHost inside the providers; it hydrates interface/task config/settings and owns navbar/dock/update UI. `AppMain.vue` uses `<router-view>` with `mode="out-in"`; keep the rendered component inside one keyed `<div>` because multi-root views otherwise break later route rendering. `router/` defines home eagerly and lazy-loads tasks/routines/logs/settings; `i18n/` mirrors zh-CN/en-US keys; `theme.ts` maps light/dark overrides and naive locales.
- `views/`: thin route composition. HomeView combines device/resource selectors, stats, presets, and routine health. TasksView composes PreTaskList, TaskSelectList, start/stop controls, StartConflictDialog, and AddTaskDialog. RoutinesView has scheduler tasks/history tabs; LogsView has the live preview stream and log panel. SettingsView has update/runtime/UI/notification/about sections plus an interface-defined task-settings section when configured, using desktop NMenu and mobile NTabs.
- `components/`: domain groups include `home/`, `logs/`, `panel/task/`, `routines/`, `settings/`, and `tasks/`; reusable descriptions and option controls live in `common/`. TaskSelectList keeps `:delay="120" :delay-on-touch-only="true"` for touch drag sorting. TaskOptionPanel/OptionItem handle recursive options and scan_select rescans; TaskSettingsDrawer is the mobile bottom drawer. SchedulerTaskDialog uses `useSchedulerTaskForm`/`useSchedulerTaskSave`/`useTaskEnvironment` plus SectionNav/TriggerType/ContentTabs; its wakeup switch is enabled only for eligible cron values.
- `stores/`: device owns connection/start/stop-then-restart; interface owns task/option/preset/settings-section getters and scan_select rescan; panel/session owns session state; scheduler owns CRUD; settings patches local state and serializes whole-document saves through a queue; task-config owns queue/order/options/presets and debounced persistence, trusts the server-normalized config, and never enables persistence after a failed load. The directly imported `focus/focus.ts` store owns the dialog queue and backend modal snapshots, with confirm/stop actions; blocking modals take priority over ordinary dialogs.
- `services/`: API modules cover task/device/interface/resource/settings/task-config/scheduler/update/notification/focus endpoints and re-export through `services/api/index.ts`; `core/types.ts` contains shared envelopes, not request machinery. Feedback contains the queued naive-ui message bridge and FocusDialogHost. Realtime is `SSEClient` with a minimal payload shape check and native `EventSource` reconnection (reopening only after the browser reports `CLOSED`), plus a dispatcher for log/toast/browser-notification/focus and task-running side effects. `focus.modal` is a state snapshot carried in `focus_modals`; its empty `message` is intentional and must survive the SSE shape check.
